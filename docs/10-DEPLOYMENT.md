# Deployment — Docker, Compose & Portainer

Design goal: **one `docker-compose.yml` + one `.env` is a complete deployment.**
Portainer's "Stacks" screen takes exactly those two things, so that's the interface
we build for.

## 1. Images

| Image            | Base                | Contents                                |
| ---------------- | ------------------- | --------------------------------------- |
| `scraper-api`    | `oven/bun:1-alpine` | Elysia server, migrations               |
| `scraper-worker` | `oven/bun:1-debian` | BullMQ consumers, Playwright client     |
| `scraper-web`    | `nginx:alpine`      | Static Vite build + runtime config shim |

All three are **multi-stage** and share a `deps` stage that runs
`pnpm install --frozen-lockfile` with `pnpm fetch` caching, then
`pnpm deploy --filter=<app> --prod` to produce a minimal runtime tree.

Notes:

- `worker` uses the Debian base, not Alpine — Playwright's client and some native
  modules are unhappy on musl. The actual browser lives in its own container.
- Non-root user (`uid 10001`), read-only root filesystem, `tmpfs` for `/tmp`.
- `HEALTHCHECK` in every image.
- Tags: `ghcr.io/<org>/scraper-<app>:<semver>` plus `:sha-<short>`. **Never deploy
  `:latest`** — Portainer's "re-pull and redeploy" on a moving tag makes rollback
  guesswork.

## 2. Compose files

```
deploy/
├── docker-compose.yml          production stack — pulls pinned images (Portainer uses this)
├── docker-compose.build.yml    build overlay for local/CI image builds
├── docker-compose.dev.yml      infra only (postgres, redis, browser) for `pnpm dev`
├── docker-compose.observability.yml   optional: otel-collector, prometheus, grafana
├── .env.example                generated by `pnpm gen:env`
├── Dockerfile.api
├── Dockerfile.worker
├── Dockerfile.web
├── nginx.conf
└── portainer/
    ├── STACK.md                click-by-click deployment guide
    └── stack.env.example       the env Portainer prompts for
```

### Production stack (shape)

```yaml
services:
  postgres:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: ${POSTGRES_USER:-scraper}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?required}
      POSTGRES_DB: ${POSTGRES_DB:-scraper}
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER:-scraper}"]
      interval: 10s
      retries: 5
    restart: unless-stopped

  redis:
    image: redis:7-alpine
    command: redis-server --appendonly yes --maxmemory ${REDIS_MAXMEMORY:-512mb} --maxmemory-policy noeviction
    volumes: [redisdata:/data]
    healthcheck: { test: ["CMD", "redis-cli", "ping"], interval: 10s, retries: 5 }
    restart: unless-stopped

  browser:
    image: ghcr.io/browserless/chromium:latest
    environment:
      CONCURRENT: ${BROWSER_MAX_CONTEXTS:-4}
      TIMEOUT: ${BROWSER_TIMEOUT_MS:-45000}
      TOKEN: ${BROWSER_TOKEN:?required}
    shm_size: 1gb                      # ← chromium crashes without this
    deploy: { resources: { limits: { memory: 2g } } }
    restart: unless-stopped

  api:
    image: ghcr.io/${GH_ORG}/scraper-api:${IMAGE_TAG:?required}
    env_file: [.env]
    depends_on:
      postgres: { condition: service_healthy }
      redis:    { condition: service_healthy }
    healthcheck: { test: ["CMD", "bun", "run", "healthcheck.ts"], interval: 15s }
    restart: unless-stopped

  worker:
    image: ghcr.io/${GH_ORG}/scraper-worker:${IMAGE_TAG:?required}
    env_file: [.env]
    environment:
      BROWSER_WS_ENDPOINT: ws://browser:3000?token=${BROWSER_TOKEN}
    depends_on:
      api: { condition: service_healthy }     # migrations land first
    volumes: [snapshots:/data/snapshots]
    deploy: { replicas: ${WORKER_REPLICAS:-1} }
    restart: unless-stopped

  web:
    image: ghcr.io/${GH_ORG}/scraper-web:${IMAGE_TAG:?required}
    environment:
      API_URL: http://api:3001
      APP_TITLE: ${APP_TITLE:-Scraper}
    ports: ["${WEB_PORT:-8080}:80"]
    depends_on: [api]
    restart: unless-stopped

volumes: { pgdata: {}, redisdata: {}, snapshots: {} }
```

`${VAR:?required}` is deliberate: Portainer fails the stack immediately with a
clear message instead of starting a container that crash-loops on a missing secret.

`web` reverse-proxies `/api` to `api`, so the whole app is one origin — no CORS,
`SameSite=Lax` cookies work, and there's one port to expose. Put your existing
Traefik/Caddy/nginx-proxy-manager in front of `web` for TLS.

## 3. Runtime frontend config

Vite inlines `VITE_*` at build time, which would mean one image per environment.
Instead `web`'s entrypoint writes `/usr/share/nginx/html/config.js` from env at
container start:

```js
window.__APP_CONFIG__ = {
  apiUrl: "${API_URL}",
  appTitle: "${APP_TITLE}",
  defaultLocale: "${DEFAULT_LOCALE}",
}
```

`index.html` loads it before the bundle, and `lib/config.ts` reads
`window.__APP_CONFIG__` with `import.meta.env` as the dev fallback. One image,
any environment — which is what Portainer users expect.

`APP_VERSION` and `GIT_SHA` are the exception: they are **build args**, baked into
all three images via Vite `define` and the API's `/health` response. They identify
the artifact, so they must not be runtime-overridable — that's what lets the client
detect a version skew after a rolling deploy and offer a reload
([04-FRONTEND §8](./04-FRONTEND.md)).

## 4. Migrations

`api` runs `drizzle-kit migrate` on boot when `RUN_MIGRATIONS_ON_BOOT=true`, holding
a Postgres advisory lock so N replicas can't race. Workers wait for the API's
health check.

Rules: migrations are **additive and backward-compatible within a release** —
expand, deploy, backfill, contract in a later release. That's what makes a rolling
restart safe and a rollback survivable.

## 5. Graceful shutdown

On `SIGTERM`:

1. Health check flips to unhealthy (proxy stops routing).
2. `api` stops accepting connections, drains in-flight requests (≤15s).
3. `worker` calls `worker.close()` — BullMQ finishes active jobs, takes no new ones.
4. `ManagedRuntime.dispose()` releases scopes: DB pool, Redis, browser contexts.
5. Exit 0. `stop_grace_period: 60s` in compose, because a Playwright run in flight
   needs it.

## 6. Portainer walkthrough (`deploy/portainer/STACK.md`)

1. **Stacks → Add stack → Repository** (Git URL, path `deploy/docker-compose.yml`).
   Repository mode gives you "Pull and redeploy" and, optionally, GitOps polling.
2. Paste env vars in the stack editor, or upload `.env`. Minimum set is in
   [11-ENVIRONMENT](./11-ENVIRONMENT.md).
3. Deploy. Watch `api` logs for migration output.
4. Register the first user, then set `ENABLE_REGISTRATION=false` and redeploy for a private instance.
5. Scale workers: edit `WORKER_REPLICAS`, redeploy. Stateless, no coordination needed.
6. Upgrade: change `IMAGE_TAG`, redeploy. Rollback: set the previous tag, redeploy.

Documented gotchas (each has bitten someone):

- Portainer's stack `.env` is **not** the same file as `env_file:` inside a
  container — we use both, and STACK.md says which is which.
- `shm_size` on the browser container is mandatory; without it Chromium segfaults
  under concurrency with an unhelpful error.
- Volumes are named, not bind-mounted, so Portainer's volume browser and backup
  tooling can see them.
- Compose `deploy.replicas` works in Swarm; on plain Docker, Portainer scales via
  the service scale control. STACK.md covers both.

## 7. Operations

**Backups** — `pg_dump` on a cron (a `maintenance` profile service, or the host's
scheduler) to a mounted volume; `snapshots` volume backed up separately or set to
`s3`. Restore is rehearsed before M4 and written down.

**Secret rotation** — `SESSION_SECRET` rotation invalidates sessions (acceptable,
users re-login). `ENCRYPTION_KEY` rotation is **not** hot-swappable: run
`pnpm ops:rotate-encryption-key --old <k> --new <k>` which re-encrypts every channel
secret in a transaction. Documented with a dry-run mode.

**Monitoring the monitor** — `/metrics` scraped by Prometheus (optional overlay
compose file); a Grafana dashboard JSON ships in `deploy/`. Alert on:
`queue_depth` growth, `scheduler_last_fire_age_seconds`, worker heartbeat staleness,
`notifications_sent_total{status="failed"}` rate, DB connection saturation.

**Logs** — JSON to stdout; Portainer shows them, and any log shipper can consume
them. No log files inside containers.

**Sizing** — a small instance (≤200 monitors, mostly HTTP strategy) runs
comfortably in ~2 GB RAM / 2 vCPU total. Browser-strategy monitors are the
expensive ones: budget ~300 MB per concurrent context.

## 8. CI/CD

```
push → typecheck · lint · unit tests · build
     → integration tests (Testcontainers: postgres + redis)
     → E2E (compose up, Playwright against the real stack)
     → build & push 3 images (buildx cache, multi-arch amd64/arm64)
     → tag release → optional Portainer webhook to redeploy
```

Multi-arch matters: plenty of self-hosters run this on ARM boxes.
