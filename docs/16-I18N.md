# Internationalization

**No user-facing string is ever written inline, on either side of the wire.**
Every sentence a human reads comes from a catalog, keyed, and resolved in that
person's locale.

Launch locales: `en` (source) and `cs`. Adding a locale is a translation file plus
one registry line — no code changes anywhere.

## 1. Where each layer's strings live

| Audience                            | Source of truth                                                       | Rendered by                               |
| ----------------------------------- | --------------------------------------------------------------------- | ----------------------------------------- |
| API error/response messages         | `packages/core/src/i18n/locales/<loc>/errors.ts`                      | API serializer, in the requester's locale |
| Emails & notification content       | `packages/core/src/i18n/locales/<loc>/notifications.ts`               | Worker, in the **recipient's** locale     |
| Web UI                              | `apps/web/src/i18n/locales/<loc>/<ns>.json`                           | `react-i18next`                           |
| Landing page                        | `apps/web/src/i18n/locales/<loc>/landing.json`                        | Same, SSG-friendly                        |
| Logs, spans, metrics, audit actions | **Not translated** — constants (see [03-BACKEND §3](./03-BACKEND.md)) | —                                         |

That last row matters: logs are for operators and machines, so they stay in one
stable language and get constants, not translations. Translating a log line makes
it ungreppable.

## 2. Backend

```ts
// core/src/i18n/keys.ts — the key tree is typed; a typo is a compile error
export const MSG = {
  errors: {
    monitorNotFound: "errors.monitorNotFound",
    planLimitExceeded: "errors.planLimitExceeded",
    rateLimited: "errors.rateLimited",
  },
  notifications: {
    changeSubject: "notifications.changeSubject",
    changeBody: "notifications.changeBody",
    runFailedSubject: "notifications.runFailedSubject",
  },
} as const

// core/src/i18n/locales/en/errors.ts — ICU MessageFormat
export const errors = {
  monitorNotFound: "Monitor not found.",
  planLimitExceeded:
    "You have reached your limit of {limit, plural, one {# monitor} other {# monitors}}.",
  rateLimited: "Too many requests. Try again in {seconds} seconds.",
}
```

```ts
// usage — a Translator service, so locale resolution is injectable and testable
const t = yield * Translator
const message = yield * t.render(MSG.errors.planLimitExceeded, { limit: 100 }, locale)
```

- Formatting is ICU via `intl-messageformat` — plurals, gender, dates, and numbers
  are locale-aware, which is exactly what a tool full of counts, prices, and
  timestamps needs. `"3 changes"` is not a string concatenation problem in Czech.
- Locale resolution order: `user.locale` → `Accept-Language` → `DEFAULT_LOCALE`.
- **Notifications resolve against the recipient**, never the request. A user with
  `cs` gets Czech alerts even when triggered by an English-locale API call.
- Numbers, currencies, and dates go through `Intl.NumberFormat`/`Intl.DateTimeFormat`
  with the user's locale _and_ their timezone. Never `toFixed`, never `toISOString`
  in user-visible output.

## 3. The wire format

Errors and any server-generated message carry **both** a rendered string and its
key, so the client can re-render in the user's chosen UI language without a round trip:

```json
{
  "code": "plan_limit_exceeded",
  "messageKey": "errors.planLimitExceeded",
  "messageParams": { "limit": 100 },
  "message": "You have reached your limit of 100 monitors.",
  "requestId": "018f…"
}
```

The frontend prefers `messageKey` when its catalog has it and falls back to
`message`. This means a locale added to the web app works immediately, even
against an older API.

## 4. Frontend

`i18next` + `react-i18next`, namespace-per-feature, lazily loaded.

```tsx
const { t } = useTranslation('monitors')
<Button>{t('actions.create')}</Button>
<p>{t('list.count', { count: monitors.length })}</p>
```

- **Type-safe keys**: `i18next` module augmentation is generated from the `en`
  catalogs, so `t('typo.key')` fails typecheck.
- Namespaces mirror features: `common`, `auth`, `monitors`, `runs`, `channels`,
  `settings`, `landing`, `errors`. A route loads only what it needs.
- Language detection: user profile → `localStorage` → `navigator.language` → `en`.
  Changing it in settings persists to the profile so notifications follow.
- `<Trans>` for strings with embedded markup or links. **Never** build a sentence
  by concatenating translated fragments — word order differs by language.
- Dates via a single `useFormat()` hook wrapping `Intl` with the user's locale and
  timezone. No component formats a date itself.

## 5. Key naming

```
<namespace>.<area>.<name>
monitors.list.emptyTitle
monitors.form.urlLabel
monitors.form.urlHelp
errors.monitorNotFound
common.actions.save
```

- Name keys after **meaning**, not the English text: `common.actions.save`, not
  `common.saveButton`. Copy changes; meaning doesn't.
- One key per distinct string. Never reuse `common.actions.save` for a verb that
  happens to look the same in English — it won't in Czech.
- Interpolate values, don't concatenate: `'{count} of {total} runs changed'`.

## 6. Tooling & enforcement

| Check                                   | Tool                                                                                                     |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| No literal user-facing strings in JSX   | `eslint-plugin-i18next/no-literal-string` (errors on JSX text and on `title`/`aria-label`/`placeholder`) |
| No hardcoded prose in backend responses | Custom lint rule: string literals in `httpError(...)` / template calls must be `MSG.*`                   |
| Missing or orphaned keys                | `pnpm i18n:check` — diffs every locale against `en`, fails CI on missing keys, warns on unused           |
| Key type generation                     | `pnpm i18n:types` — regenerates the augmentation; CI fails if the output is dirty                        |

Untranslated keys in a non-source locale **fall back to `en` and log once** — a
half-translated locale degrades, it never renders `monitors.list.emptyTitle` to a user.

## 7. Practical rules

1. Write the `en` string and its key in the same commit as the feature. A follow-up
   "add translations" ticket never gets done.
2. Give translators context in the key file as a comment when a string is ambiguous
   (`// verb, button on the monitor form`).
3. Design for text expansion: Czech and German run 30–40% longer than English.
   Buttons and labels must not be fixed-width — see [15-DESIGN-SYSTEM](./15-DESIGN-SYSTEM.md).
4. Pseudo-locale `en-XA` (`pnpm dev --pseudo`) wraps and lengthens every string, so
   truncation and untranslated leaks are visible before a real translator sees them.
